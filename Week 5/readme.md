# Week 5 – Token Economics: Cost and Rate-Limit Budgeting

## 📌 Project Overview

Week 5 focuses on understanding Token Economics and estimating the cost and resource requirements of an LLM-powered application before building it.

The main objective of this experiment is to develop a Python-based Token Budget Planner that estimates how many input and output tokens an application may consume, calculates the expected API cost, and checks whether the expected traffic fits within the provider's rate limits.

The project uses configurable assumptions such as daily requests, average input tokens, average output tokens, peak requests per minute, token pricing, and monthly budget. These values are stored in a `.env` file and loaded into the Python application.

The program calculates daily and monthly token consumption, estimates API costs, applies a safety margin, and checks Requests Per Minute (RPM) and Tokens Per Minute (TPM) limits. Finally, it generates a budget report with a recommendation indicating whether the proposed LLM feature is within the configured planning limits.

## 🎯 Objectives

- Understand input tokens, output tokens, and total tokens.

## 📖 Concepts Covered

### 1. Input Tokens

Input tokens are the tokens sent to the language model. They include system instructions, user prompts, conversation history, retrieved context, and tool descriptions.

### 2. Output Tokens

Output tokens are the tokens generated by the language model in response to the user's prompt.

### 3. Total Tokens

Total tokens represent the sum of input and output tokens.

**Formula:**

Total Tokens = Input Tokens + Output Tokens

### 4. Requests Per Minute (RPM)

RPM represents the maximum number of requests allowed per minute by the AI provider.

### 5. Tokens Per Minute (TPM)

TPM represents the maximum number of tokens that can be processed per minute according to the provider's quota definition.

### 6. Token Pricing

Token pricing represents the cost charged by the provider for processing input and generating output tokens.

### 7. Safety Margin

A safety margin provides additional capacity to handle unexpected traffic, estimation errors, and retries.

```env

```

These are illustrative values from the lab. Actual token prices and provider limits should be configured according to the selected model and service tier.

### 5. Create budget.py

Create a Python file named `budget.py`.

The program uses the following components:

- `load_dotenv()` – Loads configuration values from the `.env` file.
- `os.getenv()` – Reads environment variables.
- `FeatureBudget` – Stores the feature's budgeting assumptions.
- `from_env()` – Loads the configuration values into the FeatureBudget object.
- `calculate()` – Calculates token usage, API cost, and capacity checks.
- `main()` – Displays the final Token Economics Report.

### 6. Implement Cost Calculation

The program calculates token consumption and estimated API costs using mathematical formulas.

**Input Tokens Per Day**

Input Tokens = Requests Per Day × Average Input Tokens

**Output Tokens Per Day**

Output Tokens = Requests Per Day × Average Output Tokens

**Total Tokens Per Day**

Total Tokens = Input Tokens + Output Tokens

**Daily Cost**

Daily Cost = (Input Tokens × Input Price + Output Tokens × Output Price) / 1,000,000

**Monthly Cost**

Monthly Cost = Daily Cost × 30

### 7. Implement RPM and TPM Checks

The application checks whether the expected traffic fits within the configured provider limits.

- RPM checks the expected peak requests per minute.
- TPM checks the expected peak total tokens per minute.
- A safety margin is applied before comparing the values with configured limits.

### 8. Implement Budget Checks

The program compares the estimated daily and monthly costs with the configured budget thresholds.

It displays:

- PASS when the configured limit is satisfied.
- REVIEW when the configured limit is exceeded.

### 9. Generate the Final Recommendation

The program checks all four conditions:

1. RPM capacity.
2. TPM capacity.
3. Daily budget.
4. Monthly budget.

If all checks pass, it displays:

`WITHIN configured planning limits.`

Otherwise, it displays:

`REVISE assumptions, limits, or design before build.`

## 🔍 What-If Analysis

The experiment also explores how changing assumptions affects the estimated cost and capacity.

| Scenario | Change | Expected Effect |
|---|---|---|
| More users | Increase daily requests | Daily and monthly costs increase. |
| Longer context | Increase input tokens | Input cost and TPM increase. |
| Longer answers | Increase output tokens | Output cost and TPM increase. |
| Traffic spike | Increase peak RPM | Capacity checks become more demanding. |
| Higher price model | Increase token rates | Estimated cost increases. |
| Reduce prompt size | Decrease input tokens | Input cost and TPM decrease. |
| Cache repeated content | Reduce repeated requests and tokens | Cost and rate-limit pressure can decrease. |
